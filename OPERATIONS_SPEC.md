# `app/operations/` + `app/reconciliation/` + `app/webhooks/` — contract

The money-safety core of Conduit Console (plan v2 §3–§5). Every Conduit **mutation** in the app goes through this service — no route calls the Conduit client's mutating methods directly. Its job: a retry, restart, double-click, second tab, or lost response can never create a duplicate payout, order, or application, and no outcome stays silently unknown.

Peer contracts: `FORM_ENGINE_SPEC.md` (forms), `IMPLEMENTATION_PLAN.md` (architecture). This spec's acceptance scenario list is the failure-mode table from a plan review held externally on 2026-08-27; that document is not in this repository.

---

## 1. The operations table

One row per **logical mutation attempt** (not per HTTP attempt):

| column | notes |
|---|---|
| `id` uuid PK | also used as `clientReferenceId` sent to Conduit wherever the DTO supports one — this is the durable matcher |
| `type` | enum, §3 |
| `actor_id`, `actor_email` | verified Actor snapshot |
| `customer_id` | nullable (`cus_…`) |
| `draft_id` | nullable FK, for form-born operations |
| `request_path`, `request_hash` | sha256 over `path + canonical-JSON body` (sorted keys, no volatile fields — the idempotency key itself and timestamps are excluded) |
| `request_body` | encrypted JSON — needed for reconciler replay; purged per retention after terminal state (together with `error`, which echoes submitted values back) |
| `reference` | nullable — the operator's own console-local note (free text, ≤128 chars). Never sent to Conduit, and deliberately **not** in `request_body`, so it is **not** in `request_hash` |
| `idempotency_key` | uuid4, generated **at row insert**, immutable for the row's lifetime |
| `state` | §2 |
| `conduit_resource_id` | nullable, set on confirm |
| `error` | problem-detail JSON snapshot (incl. `correlationId`) on reject |
| `attempt_count`, `reconcile_count` | |
| `created_at`, `in_flight_at`, `resolved_at`, `unknown_since` | |

**Uniqueness — the double-submit guard:** partial unique index on `(type, request_hash)` **where state in (`created`,`in_flight`,`outcome_unknown`,`stalled`)**. Submitting an identical body while an equivalent operation is active resolves to the *existing* row (insert → conflict → select), and the UI redirects to its status page. A second tab and a rapid double-click are therefore the same row and the same idempotency key by construction. `stalled` counts as active — it is unresolved and retryable, and the original call may have landed; it is released only by an explicit, audited admin abandonment (or by resolving). Once a row is truly terminal (`confirmed`/`rejected`/`abandoned`), the index no longer blocks — an intentional identical resubmit becomes a new operation. *(Corrected 2026-08-28 — the original rule excluded `stalled` and was unsafe.)*

**The internal reference does not participate (added 2026-08-30).** `reference` is an operator's label on an attempt, held in its own column and in nothing else — so the guard above is unchanged by its existence: an identical body resubmitted under a *different* note while the first operation is still active resolves to that same operation, because it is the same payment. It is also never on the wire; Conduit's `clientReferenceId` remains `op.id`, injected at call time (§5), and is a different thing entirely.

**Counterparties are console-local and are not operations (added 2026-08-30).** A saved counterparty (`counterparties`, migration 0007) is never sent to Conduit *as a record*: Conduit's only server-side recipient store is `whitelist-recipients`, which exists for the `intercompany` gate, and `FiatPayoutDto.destination.recipient` has no by-id form — so a counterparty's fields are **pasted into the payout body at use** and travel as ordinary typed values. Saving, renaming and archiving one therefore make no Conduit call and get **no operations row**: there is no remote resource to duplicate, no idempotency key to reuse and no outcome that can stay unknown. They are plain audited writes (`counterparty.save` / `.rename` / `.archive`), the same treatment as the non-mutating exceptions listed in `app/web/__init__.py`. The payout that *uses* a counterparty is ledgered exactly as before — the destination's provenance changes nothing about the body, the hash or the guard.

**Which counterparty a payout used is an audit row, not a column (added 2026-08-30).** The `operations` table gains nothing: the trail already carries an `operation_id` FK for facts of exactly this kind (`conversion.option_selected` has always used it), and a **label recorded at the time** is what the payout was addressed from even after the counterparty is renamed or archived — which a foreign key would silently rewrite. `counterparty.used` is written by `POST payouts/new` on a *new* operation whose submission named a saved destination (a replay resolving to an existing operation records nothing — it used nothing twice); `counterparty.save` is written on 202 acceptance and now carries the same `operation_id`. The transaction's operation panel reads the newest of the two back (`counterparties.attached_label`) and renders **the label only** — never coordinates, masked or otherwise. Nothing here touches `request_body`, `request_hash`, the guard or the wire.

**Editing and deleting a contact are audited writes too, and neither may carry a coordinate (added 2026-08-31, the contact-editing round).** `counterparty.edited` and `counterparty.deleted` join `.save` / `.rename` / `.archive` as plain audited writes: still no Conduit call, still no operations row, still committed in the caller's transaction. Two rules bind their `detail`. **Masked identity diffs only:** an edit records `{"identity": {"accountNumber": "••••6789→••••6999"}}` for the `IDENTITY_KEYS` that actually changed — `counterparties.diff`, which applies this console's one masking policy (account numbers and IBANs by their last four; `routingNumber`, `bic` and `legalName` plainly, exactly as every list prints them), plus the dotted **names** of every other leaf that moved and no values for them. A label is recorded in the clear: it is what the operator called the record, not PII. **A delete records no coordinate at all**, masked or otherwise — there are none left, and a trace of the destroyed thing is the one thing a deletion may not leave behind. The deletion itself is `counterparties.purge`: the encrypted payload is overwritten with an empty object and `archived_at` is coalesced, so the row's id, label, actor, timestamps and whole trail survive and every `counterparty.used` row still resolves to a name (§3's retention rules are unchanged — this is an operator action, not a schedule). The bridge gains `counterparty.bridged` on the same terms: the contact id and label against the `whitelist_create` operation, written before the call like the shortcut's row, carrying no coordinates.

**A payout batch is not an operation either (added 2026-08-31).** `payout_batches` + `payout_batch_rows` (migration 0008) hold an uploaded CSV and what this console made of it: the route it was validated for, the sha256 of the requirements response it was validated *against*, one row per line with its assembled `destination` subtree (`EncryptedJSON`, the counterparty posture) and its validation errors. Uploading, marking ready and abandoning make **no Conduit call at all** — there is no remote resource to duplicate, no idempotency key to reuse and no outcome that can stay unknown — so all three are plain audited writes (`payout_batch.uploaded` / `.documents` / `.ready` / `.abandoned`; dispatch adds `.dispatch` when a run starts and `.dispatched` when it ends, carrying the split), the same treatment as the counterparty writes above. The batch-level shared documents obey §3's attachment rule unchanged: every `doc_` id is resolved through `documents.attachable` (purpose `transaction_support`, uploader = the submitter) before it is stored on the batch, exactly as the payout form resolves its own.

**Dispatch is where the ledger starts (added 2026-08-31).** One `payout_create` per valid row, sent sequentially, with

```python
BATCH_INTENT_NAMESPACE = uuid.UUID("9c1a4f6e-3b52-4d18-9f7a-2c0e5b8d41a3")   # fixed, forever
intent = uuid.uuid5(BATCH_INTENT_NAMESPACE, f"{batch_id}:{row_number}")      # app/batches.py
```

A form's nonce is minted per render, which is what makes a *fresh render* an intentional new attempt (above). A batch row has no render and must never have an intentional second attempt, so its nonce is **derived**: a pure function of two values that never change, identical across processes, restarts and days. `start()` resolves by intent first and in every state, so a re-click, a reload, a re-dispatch after a partial failure and a worker killed mid-batch all reach the same place — `is_new=False`, nothing on the wire, the row keeps the operation it already had. That is why `(batch_id, row_number)` is unique in the migration, why a row's number is never renumbered, and why a *correction* is a new batch rather than an edit: rewriting a row in place would change what an already-issued nonce means. `payout_batch_rows.operation_id` is the link, written before the send.

**The duplicate guard is scoped for batch rows (added 2026-08-31).** `request_hash(path, body, scope="")` takes an optional local salt, and `operations.start(..., hash_scope=…)` passes it; batch dispatch passes `f"{batch_id}:{row_number}"` — the same identity the intent is derived from. Two rows of one file may be **byte-identical and still be two payments** (two invoices to one supplier), and nothing in the body distinguishes them: `clientReferenceId` is injected at send time and is deliberately absent from the hash (§5). Without the scope, row 2's `start()` missed on intent and then hit the `(type, request_hash)` active-state guard while row 1's operation was still active (a 503 → `outcome_unknown`, or a concurrent second loop), resolving row 2 to **row 1's** operation with `is_new=False` — the row was linked to a foreign operation, counted as already dispatched, and never sent. An under-payment in which two rows claim one transaction.

The salt is **console-local**: `request_hash` feeds nothing but the partial unique index, so nothing Conduit sees changes, and the index itself needs no migration — the salted values simply differ, so two identical active batch operations insert cleanly. Form callers pass no scope and hash byte-identically to before, which is correct for them: for a form, an identical body *is* the same payment submitted twice, and that guard is the cross-tab belt §1 opens with. Only a caller that can prove its rows are distinct may declare a scope.

Three consequences are rulings rather than mechanics, and the UI states each one:

* **A rejected row is terminal in the batch.** Re-sending it would need either the same intent (which resolves to the refusal) or a new one (which would be a second payment identity for the same row). Neither is offered: the correction path is export the results → fix those rows → upload a new batch, the same rule upload sets for a failed validation.
* **A row refused *before sending* is not.** When a contact is archived, or a whitelist registration revoked, between "ready" and "dispatch", the row is refused with a stated reason in `payout_batch_rows.dispatch_error` and **nothing reaches Conduit** — so dispatching again re-resolves it and may send it. The two are distinguished by whether an operation exists, never by wording.
* **Abandoning a batch is legal only from `validating` or `ready`** (enforced by `batches.LEGAL_STATUS` and by the route). Once a row has an operation, "abandoned" would be a claim this console cannot make about money Conduit already holds. After dispatch the exits are each row's own terminal state and the batch's completion (`dispatched` once every valid row has a terminal-or-unknown operation, or a refusal).

A row whose outcome is unknown is the reconciler's, unchanged: `payout_create`'s §3 recipe looks it up by `clientReferenceId` and resolves it. Dispatch never re-sends it and offers no button that would.

**The funding account is re-read before the loop (added 2026-09-02).** `payout_batches.virtual_account_id` and `.asset` are chosen at *upload*, because the totals an operator approves are in a currency and only the account states one — and they then go into every row's body. Dispatch re-reads requirements and the whitelist live for exactly the reason the stored copy may be stale, and this one fact was the exception: taken on trust from a row that may have been written days earlier, over an account that can be closed in between. So dispatch now reads it (`accounts.fetch_account`, by id — the picker's list is pre-filtered to active accounts, which would collapse "gone" and "closed" into one absence) and refuses the whole batch when it is unreadable, gone, not `active`, or holding an asset other than `batch.asset`. The refusal is `_abort`'s existing shape — one sentence onto every pending row's `dispatch_error`, **no operation row written** — and it runs first, so an unfundable batch costs no discovery reads either. An unreadable account is deliberately not a missing one: only one of the two is fixed by pressing the button again.

A changed body = a new `request_hash` = a new operation with a new key. That matches Conduit's semantics (same key + different body → `409 IDEMPOTENCY_KEY_CONFLICT`), and it is why "fix the form and resubmit after rejection" needs no special casing.

**Intent nonce (added 2026-08-28):** the active-state hash guard alone does not survive a *lost redirect*: once the first operation confirms, the guard releases, and a browser mechanically re-POSTing the same form (connection retry, back-button resubmit) would mint a second operation and pay twice — that retry is not an "intentional resubmit". Therefore every mutation form render mints a one-use `intent` uuid (hidden field, stored on the operation row, unique index across **all** states). `start()` resolves an existing operation by `intent` FIRST, regardless of state — the same rendered form always maps to the same operation forever. A fresh render mints a fresh intent; that is what "intentional new attempt" means mechanically. The hash guard remains as the cross-tab/second-render belt over active states.

**A nonce that loses to the hash guard is recorded too (added 2026-09-02).** `operations.intent` can only ever hold the nonce that *created* a row, and that left a hole exactly where the two guards meet. When a submit's nonce missed and the active-state hash guard then resolved it to an operation some *other* render created, the submitting nonce was written down nowhere — so guard 1 could never answer it again. The operation then went terminal, the hash guard released with it, and the next mechanical re-POST of that same form (the lost redirect this nonce exists for) missed both guards and minted a second payment with a second idempotency key. The `stalled`-counts-as-active correction closed the same hole for active states; this is its terminal-state half.

Therefore the mapping is its own table, **`operation_intents(intent uuid PK, operation_id FK → operations.id, created_at)`** (migration `b8e41d7c2a95`): one row per nonce, naming the operation that nonce **reached** — whether it created it or the hash guard resolved it there. `by_intent` reads this table and nothing else, so guard 1's promise ("the same rendered form always maps to the same operation forever") now holds for both routes in, terminal or not, with no second idempotency key available anywhere. The row is written in the same transaction as the operation it names, and the primary key makes "one nonce, one operation" a database constraint rather than a convention.

`operations.intent` is **kept**, and keeps its unique index: that index is what arbitrates two concurrent posts of one nonce into a single row — it is enforced by the insert itself, before any `operation_intents` row can exist — and the column then reads as *the nonce this operation was created by*, which is a different fact from *a nonce that reached it*. A creating insert whose nonce turns out to be already claimed (reachable only when a racer took the hash-guard branch against an unrelated same-body operation going terminal mid-race) is discarded and re-resolved rather than tolerated, because the alternative is `by_intent` pointing at an operation the render did not produce.

**The lookup is scoped to the operation type (added 2026-09-02).** `by_intent` takes the submitting form's own `type`, and a nonce that reached an operation of another type is **refused** (`IntentTypeMismatch` → a 422 problem box; `create_app` registers the handler, and the payouts form re-renders with the operator's values). Refused rather than filtered: filtering would read as "this nonce reached nothing", and the submit would then mint a second operation under a nonce that is already spent — two operations answering to one nonce, with which one a later replay resolves to decided by write order.

**What this does not change:** a *fresh* nonce is still an intentional new attempt. A refused payout re-rendered with a new nonce still creates a new operation — the promise the Execute panel's own copy makes about funding an `INSUFFICIENT_FUNDS` order and pressing again. Only a nonce that has already reached an operation is bound to it.

**And the polled-region half, which the table cannot reach (added 2026-09-02, same item).** On `orders/detail.html` and `operations/detail.html` the mutating forms live inside regions that replace themselves on a 15s timer, so every poll re-renders them and mints a *fresh* nonce. Persisting intents makes a **consumed** nonce resolve forever; here the nonce is never consumed — it is discarded, unasked, before the operator's next press can carry it, and a fresh nonce is by definition a new attempt. So the two fixes are complementary, not alternatives, and `operation_intents` alone leaves this window open. The mechanism is `static/app.js`'s `pollBlocked`: an `htmx:beforeRequest` listener that `preventDefault()`s a request whose triggering element is a polled region (`hx-trigger` beginning `every `) currently containing a `form.htmx-request`. Only the poller is paused — a request the operator started, the submit that made the region busy included, always goes through — and only while a submit from that region is in flight, so the actions stay as fresh as the status they are derived from. Written as a listener rather than an `hx-trigger` `[…]` filter because those are `eval` and this console ships `script-src 'self'`. The two fixes the 2026-09-01 analysis rejected stay rejected: a deterministic nonce breaks the legitimate retry the page's own copy promises, and freezing the action row turns a latent nonce issue into a live lying affordance.

## 2. State machine

```
created ──► in_flight ──► confirmed          (2xx; resource id recorded)
   │            │────────► rejected           (definitive 4xx; problem-detail stored)
   │            │────────► outcome_unknown    (timeout, conn error after send, 5xx,
   │                                           or stale in_flight found by reconciler)
   │
   └──► abandoned                             (never sent; draft discarded / TTL)

outcome_unknown ──► confirmed | rejected      (reconciler resolves, §4)
outcome_unknown ──► stalled                   (reconciler gives up after N attempts)
stalled ──► in_flight                         (explicit operator retry, same row+key;
                                               resets reconcile_count/unknown_since)
stalled ──► confirmed | rejected              (evidence only: an observation —
                                               webhook or reconciler read — proves the
                                               resource's real outcome; system actor,
                                               audited. Stalled means "we stopped
                                               looking", not "we stop listening.")
stalled ──► abandoned                         (admin release valve, audited)
```

| transition | performed by |
|---|---|
| `created → in_flight` | web, immediately before the HTTP call (timestamp `in_flight_at`) |
| `in_flight → confirmed/rejected/outcome_unknown` | web, on response/exception |
| `in_flight → outcome_unknown` | **reconciler**, when `in_flight_at` older than 2× client timeout (process died mid-call) |
| `outcome_unknown → confirmed/rejected/stalled` | reconciler only |
| `stalled → in_flight` | web, only via an explicit, audited operator action — **resets `reconcile_count` and `unknown_since`** so a lost retry response gets a full reconciliation cycle |
| `stalled → abandoned` | admin only, explicit + audited — the release valve for the §1 uniqueness guard |
| `created → abandoned` | worker TTL job |

Rules: transitions are row-locked (`SELECT … FOR UPDATE`); illegal transitions raise; every transition appends an `audit_events` row (actor = operation's actor, or the system actor for worker/reconciler). Terminal states never regress. The write sequence is always: **insert `created` + commit → set `in_flight` + commit → call Conduit → record result + commit** — so a crash at any point leaves a row the reconciler can find.

**Definitive vs ambiguous responses:** 2xx → confirmed. 4xx with a parsed problem-detail → rejected (except `409 IDEMPOTENCY_KEY_CONFLICT`/`ONBOARDING_ALREADY_SUBMITTED`-class conflicts, which mean "Conduit already has it" → treat as outcome_unknown and let the reconciler find the resource). 5xx, timeout, connection reset after send → outcome_unknown. Connection failure provably *before* send (DNS, connect refused) → stay `in_flight`→ back to `created` is NOT allowed (keep it simple: also outcome_unknown; the reconciler's not-found path handles it safely).

## 3. Operation types and reconciliation recipes

`clientReferenceId = operation.id` is sent on every type whose DTO supports it. Recipes run in order; first hit wins.

| type | Conduit call | resolve `outcome_unknown` by |
|---|---|---|
| `onboarding_submit` | `POST /v2/onboarding` | 1. `/v2/applications` **has no `clientReferenceId` query param** (verified against the pinned spec) — pull a recent page (narrowed by `customerId` where known) and match `clientReferenceId` locally on the returned DTOs → confirmed. 2. Not found → replay same body + same key (§4 replay rules). |
| `customer_update` | `POST /v2/customers/{id}/updates` | same as above (produces an application) |
| `feature_request` | `POST /v2/customers/{id}/features` | **`FeatureRequestDto` carries no reference field** (verified): match a recent application on `customerId` + feature `type` + asset code + `createdAt ≥ op.created_at − 60s` → confirmed. Else replay. |
| `document_upload` | `POST /v2/documents` | No reference field: replay with same key; a duplicate document is harmless (worst case an unused `doc_` id) — documented low-risk exception. **Resolved 2026-08-28:** uploads are multipart binary, so the file lives Fernet-encrypted in `document_blobs` (one row per operation; filename, sniffed content type, sha256, size, purpose, name) and the operation's `request_body` carries only `{fileSha256, purpose, name, scope}` — which makes `request_hash` = sha256 over path + canonical JSON of those four, so the §1 double-submit guard covers uploads unchanged. **`scope` (`customer_id` → `draft_id` → `actor_id`) added 2026-08-28:** without it the hash was the file alone, so two operators attaching one shared document to two customers collapsed into a single operation and the second upload silently inherited the first's `doc_` id. Intake enforces ≤10 MB and PDF/JPEG/PNG **by magic bytes plus a structural check** — PDF `%%EOF` in the last 1 KB, JPEG EOI in the last 32 bytes, PNG `IHDR` at offset 12 — so a truncated or header-prefixed file is refused (the filename and `Content-Type` are caller-supplied; Conduit re-validates server-side, this is a gate rather than a guarantee). `app.conduit.execute.send()` rebuilds the identical multipart body for the first attempt and for every replay; blob bytes are purged by the §6 rules, and a missing blob leaves the operation `outcome_unknown` rather than sending an empty file. |
| `rfi_respond` | `POST /v2/rfis/{id}/responses` | `GET /v2/rfis/{id}` → responses[] contains our round response → confirmed; 409 on replay = confirmed. `documentIds[]` is subject to the attachment rule below. |
| `whitelist_create` | `POST /customers/{id}/whitelist-recipients` | List recipients, match on `(legalName, rail, relationship, bank coordinates)` **and** `status in (pending_review, registered)` **and** `createdAt ≥ op.created_at − 60s` → confirmed. Else replay. *(Verified 2026-08-28: unused coordinates read back as explicit `null`, and the request omits them, so the match is over the keys the body actually carried.)* **Narrowed 2026-08-28:** `(legalName, coordinates)` alone matched the residue of an *earlier* registration of the same account — a revoked entry, or the same bank account registered on another rail — so a lost response confirmed against somebody else's dead row and the new registration was never made. The four extra predicates are what make the match specific to *this* attempt: a terminal-status entry cannot be a registration we just created, and neither can one that predates the operation. |

Not found → replay same body + same key. **Never a fresh key.** *(`type` is a **required** query parameter — corrected 2026-08-28: without it the lookup 400s, which reads as "could not tell", so the recipe never confirmed and every unresolved payout walked to `stalled`. Fail-safe, but never resolving.)* |

| `order_execute` | `POST /v2/orders/{id}/execute` | Read the order: past `pending` → confirmed; still executable → replay. |
| `order_cancel` | `POST /v2/orders/{id}/cancel` | Read the order state, as payout_cancel. |
| `webhook_endpoint_register` | `POST /v2/webhooks/endpoints` | List endpoints, match URL → confirmed. |

**Attachment rule — a document id on a form is an assertion, not a fact (added 2026-08-30, extended to the money paths in the same round).** Three submits let the browser name documents that Conduit then stores against something of ours: `rfi_respond`'s `documentIds[]`, and `payout_create`'s `documents[]` — which the payout form *and* the transfer screen both produce, through the one `payments.payout_body`. All three forwarded whatever ids arrived, so any `doc_` id an operator could guess or had seen elsewhere could be published under this organisation's name and attached to a compliance answer or to a payment. Nothing downstream re-checked it: Conduit's validation is org-wide, which is precisely the boundary being crossed.

Every id is therefore resolved, **before `operations.start`**, against this console's own upload ledger: a `confirmed` `document_upload` operation whose blob carries the **matching purpose** (`rfi_response` for an RFI answer, `transaction_support` for a payout or transfer) **and whose actor is the submitter** — or, for onboarding, whose draft is the one being submitted (see below) — (`documents.attachable` / `documents.unattachable`). One unmatched id refuses the whole submission — the money forms re-render 422 with the complaint on the upload widget and the operator's values intact, the RFI panel redirects to its subject page; the sentence is one constant so the three cannot drift apart. Uploader-actor is not a preference but the only scope these rows hold: neither an `rfi_response` nor a `transaction_support` upload carries a customer id (`web/onboarding.upload` passes the actor, and a `draft_id` only for onboarding), so a "same customer" rule would have to invent the association it claims to check. Both columns it reads outlive the §6 retention purge, which empties bytes and names but never `purpose`.

**Extended to the remaining three submits (2026-09-05).** Onboarding's `documentIds[]` (root and per-person), the whitelist registration's `evidenceDocumentIds` and the feature request's `documentIds` were previously out of scope, on the reasoning that the draft's own ownership check already gated who may submit. It does gate *who submits*; it never gated *which documents ride along*. A `doc_` id harvested from the operations panel (`operations/_panel.html`) or simply guessed was forwarded verbatim, and the upstream accepted the registration for review — so another customer's identity document could back this customer's application, and Conduit's org-wide validation is precisely the boundary that cannot catch it. All six submits now resolve every id before `operations.start`, refusing with the same one constant.

Onboarding scopes by **draft**, not by uploader-actor, and that is deliberate rather than a weakening. The split editor/reviewer deployment — the one the reviewed-payload seal exists for — has the editor upload and the reviewer submit, so an uploader-actor rule would refuse every reviewer submission of a draft carrying a required document. The draft is itself the access boundary (`_draft` 404s a draft that is neither yours nor reachable with the admin-only `onboarding.access_any`, and `upload` goes through it), and draft-scope is strictly *tighter* than actor-scope on the exposure this rule exists for: it refuses the same actor's own other application, which actor-scope does not. `documents.unattachable` raises rather than defaulting when given neither scope, so "no rule at all" cannot be reached by omitting an argument.

**§4 Replay rules (reconciler):** replay = the original body with the original `Idempotency-Key`. Within Conduit's key-cache window this is a pure read of the cached response. Beyond the window it *could* create the resource — which is exactly the desired outcome, because step 1 of every recipe has already proven by reference lookup that the resource does not exist. Replay only after the reference lookup misses; look up again after an ambiguous replay. After `RECONCILE_MAX_ATTEMPTS` (default 5, exponential spacing: ~1, 2, 5, 15, 60 min) → `stalled`.

**Definitive-conflict short-circuit (added 2026-08-28 post-v1, from live sandbox evidence):** at mutation time every 409 stays ambiguous (classify() is right — a conflict must never be mislabeled). But in the *reconciler*, once the reference lookup has missed (proving our operation created nothing) and the replay answers a conflict whose `type` is in the `DEFINITIVE_CONFLICTS` allowlist — refusals that name a *pre-existing other* resource, e.g. `CUSTOMER_ALREADY_ONBOARDED` (carries `details.customerId` of the existing customer), `WHITELIST_RECIPIENT_CONFLICT`, `APPLICATION_ALREADY_DECIDED` — the operation resolves **`rejected`** immediately with the full problem-detail (and the named existing resource surfaced in the UI), instead of riding the backoff to `stalled`. Conflicts implying Conduit holds *our* resource (`IDEMPOTENCY_KEY_CONFLICT`, `ONBOARDING_ALREADY_SUBMITTED`-class) are NOT in the allowlist — those still resolve by lookup. The allowlist is explicit and conservative: an unlisted conflict type keeps today's behavior. Caveat for future entries: the lookup-miss precondition is vacuous for recipes with no reference lookup (`document_upload`) — never allowlist a conflict type for such a type without adding a real absence proof first.

Reads performed by the reconciler follow the client's read policy (Retry-After on 429, jittered backoff), and reconciler throughput is capped so it can never contribute to rate-limit pressure against interactive traffic.

## 4. Webhook inbox

- Endpoint handler (web role): read **raw body bytes**, verify `X-Conduit-Signature` (HMAC-SHA256 over `{t}.{rawBody}`, key includes `whsec_` prefix, 300s tolerance, accept any matching `v1` during rotation) → `INSERT … ON CONFLICT DO NOTHING` into `webhook_events` keyed by the event's unique id (fallback: sha256 of raw body) → `200` immediately. No processing in the request path. Invalid signature → `400`, logged, not stored.
- Worker: processes pending inbox rows. Handlers are **idempotent and state-monotonic** — they funnel into the same `apply_observation()` used by the reconciler.

**Stale-projection sweep (plan v2 §5's repair job).** Webhook delivery is at-least-once, not exactly-once: a delivery that never arrives leaves a projection stuck mid-flight forever, and the operation reconciler never looks — it only visits rows with an unresolved *operation*, which a settled-but-mis-projected resource does not have. So every `reconcile_pass()` ends by re-reading each non-terminal projection older than `PROJECTION_STALE_SECONDS` (default 15 min) *exactly, by id*, and feeding the result through `apply_observation()`. It shares the pass's request budget (operations first — an unresolved mutation is the more urgent unknown) and is capped at `PROJECTION_SWEEP_LIMIT` rows per tick. Only kinds readable from an id alone are swept — `transactions`, `applications`, `orders`, `rfis` (§5: for RFIs this sweep is the *primary* source of state, not a repair, because their events carry only an id); `virtual_accounts` and `whitelist_recipients` live under `/v2/customers/{customerId}/…` and the projection row carries no customer id, so they stay covered by webhooks and by their operations' own recipes until it does. An unreadable resource is left stale, never guessed at.

**Selection is entirely in the query (corrected 2026-08-30).** The cap is a `LIMIT`, so anything filtered *after* it can starve everything behind it: with the terminality check in Python, fifty old settled projections — which a working ledger accumulates by design — filled every batch and were then all skipped, and a newer stale row was never reached on any tick for as long as they stayed oldest. Terminality is per-kind, so the predicate is the `(kind, state)` pairs of `projections.TERMINAL` rather than a list of words; a row with **no** state is not settled and must be selected (`NOT (NULL IN …)` is NULL, which would drop it). One deliberate exception is selected *because* it is terminal: an RFI whose first observed event was `rfi.resolved`/`rfi.cancelled` holds an id and a status and no `subjects`, and would otherwise stay a row that cannot say what it was about — it gets exactly one hydration read, after which the stored `ClientRfiDetailDto` has subjects and the predicate stops selecting it.

Because the sweep exists, a **failed projection write is a recoverable state rather than a lost one**: `_project()` runs after the operation transition has committed (it must — `apply_observation` resolves operations itself and would otherwise steal the verdict the pass just earned), so a failure there is caught, logged, and left for the sweep. It never propagates back into the operation, which is already correctly `confirmed`; un-confirming a resolved mutation to report a bookkeeping failure is the one outcome worse than a stale row.

**`apply_observation(resource_kind, resource_id, observed, observed_at)` — the single projection writer.** Both webhook handlers and reconciler reads call it; nothing else writes projections. It row-locks the projection and applies the observation only if it advances state (terminal beats non-terminal; newer `observed_at`/`updatedAt` beats older; equal-rank different values → keep newer and log a drift warning). Out-of-order and duplicate deliveries are thereby no-ops, and the webhook-vs-reconciler race disappears: last-to-arrive still can't regress a projection. If the observation confirms/settles a resource tied to an operation row (matched by `conduit_resource_id` or clientReferenceId), the operation is resolved through the same locked transition path as §2.

## 5. Operator-facing contract

- `outcome_unknown` renders as **"Result being confirmed"** with the operation id, what was attempted, and auto-refresh — never a retry button.
- `stalled` renders as **"Couldn't confirm — needs attention"** with the full trail (attempts, timestamps, last error + `correlationId`) and one explicit, audited **Retry** action (same row, same key) plus a "mark abandoned" for admins. Copy tells the operator what to give support.
- `rejected` renders the problem-detail: `title`, `detail`, `resolution`, `correlationId`, and mapped field errors where applicable. A **locally-minted** rejection (e.g. `RESOURCE_NOT_ACTIONABLE` — the reconciler determined "too late to cancel" from resource state) has no `correlationId`; the UI labels it "determined from Conduit's records" and shows the resource id instead of a correlation id.
- **`POST /v2/quotes` is the one endpoint that refuses an `Idempotency-Key`** (verified live 2026-08-28): `400 VALIDATION_ERROR`, *"Idempotency-Key is not supported on this endpoint — a replay always reprices, so caching a response here would…"*. It is also the one mutation-shaped call that is **not** ledgered: a quote creates nothing, reserves nothing and can never leave an outcome unknown, so the payout route calls `client.mutate` with no key and no operation row. Everything else in §3 still sends the header unconditionally.
- Implementation notes (verified live): `clientReferenceId` is injected into the outbound body at call time — never stored in `request_body`, or every `request_hash` would be unique and the §1 double-submit index would never fire. All 409s and 429s classify as ambiguous at mutation time (a conflict is never mislabeled as a rejection; the recipe reaches the correct terminal state one read — or, for §4 allowlisted definitive conflicts, one replay — later). `Idempotency-Key` is sent on every mutation including endpoints whose spec doesn't declare it — **verified live 2026-08-28**: `POST /v2/documents` declares no `Idempotency-Key` parameter and accepted one without complaint (`201`), as did `POST /v2/onboarding`, which does declare it. Sending it unconditionally is safe.
- Status pages read operation + projection state; they never issue Conduit mutations.

**Supporting documents: both worlds, no feature flag (added 2026-08-30).** Today a required-but-missing document is a **synchronous** refusal — `422 DOCUMENTATION_REQUIRED`, no payout created, operation `rejected`, guard released — and the pinned spec still says exactly that. Conduit has announced the opposite: the transaction will be **accepted** and an RFI raised against it. The console runs both without a branch, because the branch it already has is the right one:

| | today | announced |
|---|---|---|
| Conduit answers | `422` | `2xx` + an RFI |
| operation reaches | `rejected` | `confirmed` |
| operator sees | the payout form again, with Conduit's problem detail and their values intact | the transaction page, badged **Held — information requested**, with the RFI's round and the respond form on it |

Both rows are pre-existing code paths. `web/payouts.submit` branches on `op.state` and never on a problem `type`, so a refusal it has never seen behaves like every other refusal; a transaction-subject RFI is read on the transaction page from `hasRfi` (Conduit's own read-time derivation, on every transaction view DTO) and projected from `rfi.*` webhooks whenever it arrives, neither of which cares how the payout was submitted. **No speculative handling of response shapes that do not exist yet** — the flip changes which branch Conduit selects, not what the console must recognise.

**RFIs are observed, never resolved-against (added 2026-08-30).** `rfis` is now a projection kind (ladder `draft` → `open`/`responded` → `resolved`/`cancelled`, the last pair terminal; `open` and `responded` deliberately share a rank because `rfi.more_info_requested` re-opens an answered RFI and that is a real transition, not a regression). §4's `apply_observation` resolution step is a **no-op** for it, and provably so rather than by convention: nothing this console can call creates an RFI, `ClientRfiDetailDto` carries no `clientReferenceId`, and the only operation that touches one — `rfi_respond` — records its `conduit_resource_id` (the `rfi_` id, since the respond endpoint answers with the RFI) *at confirmation*, which is after the states `_resolve_operations` matches on. An `rfi.*` observation therefore has nothing to resolve.

**`responded` is Conduit's turn, not ours (corrected 2026-08-30).** The console offers a respond form for `open` only. `rfi.response_submitted` moves an RFI to `responded`, and the sole route back to the operator is `rfi.more_info_requested`, which sets it to `open` again — so a form on a `responded` RFI invited a second, unasked-for response, and the "held / awaiting answer" labelling on a transaction claimed a debt that had already been paid. `responded` still counts as open on the `/rfis` index (it is live, and its deadline still matters); it is simply not actionable here.

The six live event types (`rfi.published`, `.more_info_requested`, `.response_submitted`, `.deadline_extended`, `.resolved`, `.cancelled` — `GET /v2/webhooks/event-types`, sandbox, 2026-08-30, all `beta`) each carry `data` of exactly `{"rfiId": "rfi_…"}`: no status, no subjects, and a description that says to fetch the rest. So the event-type **suffix** is the whole of the state a delivery carries (`worker.STATE_BY_SUFFIX`; `deadline_extended` asserts none — it moves `dueAt`), and §4's stale sweep is load-bearing here rather than a last-resort repair: `GET /v2/rfis/{id}` reads from the id alone and returns a required `status`, so `rfis` joins `transactions`/`applications`/`orders` in `PROJECTION_READ_PATH`. The `rfi_respond` recipe still projects nothing — its `Found` names the *response*, not the RFI, and the webhook plus the sweep already cover the RFI itself.

## 6. Configuration

`OP_CLIENT_TIMEOUT` (default 30s) · `OP_STALE_INFLIGHT_FACTOR` (2×) · `RECONCILE_MAX_ATTEMPTS` (5) · `RECONCILE_INTERVAL` (60s sweep for stale in_flight + due outcome_unknown) · `PROJECTION_STALE_SECONDS` (900 — a non-terminal projection untouched for longer is re-read by the §4 sweep) · `OP_CREATED_TTL` (24h → abandoned) · `OP_BODY_RETENTION` (purge `request_body`, **`error`** — Conduit's problem detail echoes submitted field values back, so keeping it kept the coordinates the purge exists to drop — **and `document_blobs.data`, `.filename`, `.name`, `.sha256`** — a filename like `Jane_Doe_passport_123.pdf` is personal data and a digest fingerprints content no longer held — 30 days after reaching `confirmed`/`rejected`/`abandoned` — **never** while `stalled`, which is retryable and needs both for byte-identical replay) · `DRAFT_TTL_DAYS` (30; unsubmitted drafts discarded by the worker tick — submitted ones are kept, their payload already purged) · `WEBHOOK_RAW_RETENTION_DAYS` (30; `webhook_events.raw_body` NULLed once the event is `processed`/`processed_ignored` and older than the window, **never** while `pending`/`processing`, and **never** when `failed`, whose body is the only evidence of why it is poison).

**`OP_BODY_RETENTION` also covers `payout_batch_rows.payload`.** A dispatched row's assembled `destination` subtree is the same data as the `payout_create` body it became, so purging one and keeping the other deleted nothing. Aged from the **batch's** `updated_at` — when its dispatch finished; a row carries only upload time — and only for a batch in `dispatched` or `abandoned`. `partially_dispatched` is excluded for the reason `stalled` is: it is re-dispatchable, and the undispatched rows still need the destinations they would be sent with. `amount`, `purpose`, `contact_label`, `errors`, `dispatch_error` and the minted operation all survive, so the results export and the ledger read the same afterwards.

**Resolved 2026-08-28** — the reconciler now feeds `apply_observation()`. A recipe's positive answer (`Found`) carries the resource kind and the resource dict it read, so found-by-reference lookups and by-status reads land in the projection through the same single writer the webhook path uses. The kind is the resource's own kind, not the path it was read through: **a payout IS a transaction** (verified against the pinned spec — `PublicTransactionsPageDto` is the unified view "across deposit / … / withdrawal / …, discriminated by `type`", and `GET /v2/payouts/{id}` returns that withdrawal branch under the same `txn_` id), so `payout_create` and `payout_cancel` both project under `transactions`, the same row a `transaction.*` webhook writes. There is deliberately no `payouts` projection kind — two kinds for one resource would mean two rows telling the same truth and a list view free to render the stale one. Applications → `applications`, orders → `orders`, whitelist → `whitelist_recipients`; recipes with nothing projectable (RFI responses, webhook endpoints) carry no kind and write nothing. The projection write happens *after* the operation transition, so the transition still reports its own verdict rather than losing the race to the observation's own resolution path.

## 7. Test plan (acceptance — these are the review's failure modes)

Integration tests against real Postgres, Conduit stubbed at the HTTP layer:

1. **Lost response drill**: stub accepts the payout then drops the connection → op `outcome_unknown` → reconciler reference-lookup finds it → `confirmed`, exactly one payout, audit trail complete.
2. **Never-arrived drill**: stub drops before processing → reference lookup misses → replay (same key) → created exactly once.
3. **Restart mid-call**: kill between `in_flight` and result-record → reconciler sweeps stale in_flight → resolves as (1)/(2).
4. **Rapid double-click / two tabs**: two concurrent identical submits → one row, one key, second caller redirected to the same operation.
5. **Changed-body resubmit after rejection**: new row, new key; old row untouched.
6. **Idempotency-conflict path**: stub returns `409 IDEMPOTENCY_KEY_CONFLICT` → outcome_unknown → resolved by lookup, never surfaced as success or generic error.
7. **Duplicate webhook**: same event twice → one inbox row, one projection application.
8. **Out-of-order webhooks**: `completed` then `processing` → projection stays `completed`; drift warning on conflicting equal-rank values.
9. **Webhook/reconciler race**: both observe the same settlement concurrently → single confirmed transition (lock contention test).
10. **Stalled path**: reconciler exhausts attempts → `stalled` → audited manual retry succeeds with the same key.
11. **429 discipline**: reconciler honors Retry-After and never exceeds its budget.
12. **Signature handling**: valid/invalid/stale-timestamp/rotated-secret vectors against the raw-body verifier (fixture-based; no live delivery needed — live webhook delivery is verified at first hosted deployment, reconciliation covers correctness until then).

## 8. Non-goals

- Exactly-once webhook delivery (at-least-once + idempotent apply is the model).
- Distributed coordination beyond one Postgres (row locks suffice for web + one worker; scaling workers later means `FOR UPDATE SKIP LOCKED` on the inbox, already compatible).
- Automatic retry of `rejected` operations, cross-operation sagas, or compensation logic — humans decide; the system only makes outcomes visible and single-shot.
